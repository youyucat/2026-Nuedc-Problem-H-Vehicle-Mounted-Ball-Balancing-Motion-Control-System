# 双芯通信协议（A ↔ B）

> 状态：**当前实现 = ASCII 行协议，可直接作为联调基线**，来源
> `stm32f411_ball/Core/Src/ball_ctrl.c`、`Core/Inc/ball_ctrl.h`。
> B 侧作者原计划后续换二进制帧，是否切换见第 7 节；**未切换前以本文档为准**。
> 修改本文件前必须双方确认——B 侧解析器按此实现，
> 单方面改 A 侧编码会造成静默丢帧（不报错、球就是稳不住）。

## 1. 物理层

| 项目 | 取值 | 来源 |
| --- | --- | --- |
| 方向 | A(MSPM0G3507) → B(STM32F411)，单向 | — |
| 接口 | B 侧 **UART1** | `main.c: huart1.Init.BaudRate` |
| 波特率 | **115200** | 同上 |
| 帧格式 | 8 数据位 / 无校验 / 1 停止位（8N1） | HAL 默认 |
| 电平 | 3.3 V TTL | 待硬件确认 |

### ⚠️ B 的 UART1 目前被 MaixCam 独占

B 侧 `ball_ctrl.c` 的注释写 ASCII 帧「与二进制共线」，指的是**软件解析器能同时容忍两种帧**：

- **MaixCam 视觉程序**：12 字节二进制帧（帧头 `0xAA 0x55`）
- **芯片 A**：ASCII 行帧（本文档第 2、3 节）

> 视觉帧的完整字段定义（CRC16-CCITT、0.1mm 单位、标志位）见
> `vision/maixcam/README.md`，与 `stm32f411_ball/Core/Inc/ball_ctrl.h` 头部注释一致。

行解析器遇到 `< 0x20` 或 `> 0x7E` 的字节会作废整行，所以二进制噪声不会被误认成 ASCII 帧。
固件这层兼容是成立的。

**但物理上不成立。** 核对 `vision/maixcam/maixcam_ball_detect.py` 后确认：

| 事实 | 出处 |
| --- | --- |
| MaixCam 把 `A19` 映射为 `UART1_TX`、`A18` 映射为 `UART1_RX`，设备 `/dev/ttyS1` | `VisionUartLink.__init__` |
| 脚本里**只有 `port.write()`，没有任何 `read`/`readline`** | 全文件检索 |

也就是说 **MaixCam 只发不收，不会做透明转发**。而 B 的 UART1 只有一个 RX 引脚，
已被 MaixCam 的 TX 占用。结论：

> **当前接线方式下，芯片 A 的 `A,<accel>` 帧没有任何物理通路能到达 B。**
> B 侧的前馈功能处于「已实现但喂不到数据」的状态。

三条可选方案，需硬件确认后择一：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **① MaixCam 转发（软件解，推荐）** | A → MaixCam 的 `A18`(UART1_RX)，脚本里加读串口 + 原样转发到 B | 需要改视觉脚本，MaixCam 多一个线程；UART1 需做成「收 A、发混合流」 |
| **② 换一路 UART** | B 改用 UART2/UART3 专接 A | 改 `MOTER.ioc` + 重新生成代码，Keil 工程要同步；但要占新引脚 |
| **③ 硬线或分时** | 二极管线与 / 模拟开关切换 | 不可靠，不建议 |

方案 ① 的额外好处：MaixCam 已有 WiFi + 网页，可顺手把 A 的加速度显示在网页上，方便联调。

## 2. 行帧格式

```
<tag> <字段1> [ , <字段2> ] [ , <字段3> ] [ * <HH> ] \n
```

| 部分 | 说明 |
| --- | --- |
| `tag` | 单字符消息类型，见第 3 节，大小写不敏感 |
| 字段 | 十进制整数，`strtol` 解析，英文逗号分隔，最多 3 个 |
| `*HH` | 可选校验：星号前所有字节的**异或**，2 位十六进制。不带校验也接受 |
| `\n` | 帧尾；`\r` 被忽略（兼容 CRLF） |
| 缓冲区 | 行长上限 `LINE_BUF_LEN = 24` 字节，超长整行丢弃 |

**容错规则**（B 侧已实现，A 侧发送时应保证不触发）：

- 行内出现不可打印字节（`< 0x20` 或 `> 0x7E`）→ 整行作废
- `*` 后没有合法十六进制数 → 整行丢弃
- 校验不符 → 整行丢弃
- 未知 `tag` → 静默忽略

## 3. 消息类型

| tag | 名称 | 方向 | 字段 | B 侧行为 |
| --- | --- | --- | --- | --- |
| `A` | 车体纵向加速度 | A → B | `accel`：mm/s²，int32 | 惯性前馈，限幅 ±1500 |
| `R` | 球目标位置 | A → B | `x`：0.1 mm 整数 | 要求 6 用，改变目标点 |
| `M` | 台架手动摆角 | 调试 → B | `mdeg`：0.001° | 手动摆杆，台架调试 |
| `Z` | 水平基准清零 | 调试 → B | 无 | 重新标定机械水平 |
| `B` | 球状态 | MaixCam → B | `x`,`v`,`conf` | 二进制视觉帧的 ASCII 等价通道 |

### A 帧（当前唯一的双芯数据流）

```
A,<accel>*<XOR>\n
```

示例：加速度 +820 mm/s²

```
A,820*57\n
```

`*57` 的算法：星号前 5 个字节 `0x41 0x2C 0x38 0x32 0x30` 依次异或 = `0x57`。
**建议 A 侧开启校验**，线路受干扰时 B 能丢弃而不是把噪声当加速度。

B 侧收到后的前馈映射（`ball_ctrl.c`）：

```c
ff_mdeg = accel_mm_s2 * 1000 * (-1) / 180;   /* 180 mm/s² ≈ 1° */
ff_mdeg = clamp(ff_mdeg, -5000, +5000);      /* 上限 ±5° */
```

即 **1° 倾角对应 180 mm/s²**，方向取反（`BALL_INERTIA_DIRECTION = -1`）。
加速度 1500 mm/s² 时按公式算得 8333 mdeg，会被限到 5000 mdeg（5°）。

## 4. A 侧待实现清单（MSPM0）

当前 `mspm0_line_follow/` **完全没有 UART**：`line_follow_mspm0g3507.syscfg` 里
无 UART 实例，`hal/hal.h` 明确写着「已移除 hal_uart」，也没有任何加速度输出。
要打通双芯，A 侧需要补三件事：

| 待办 | 位置 | 说明 |
| --- | --- | --- |
| 1. SysConfig 增加 UART 实例 | `*.syscfg` | 选未被占用的引脚（注意别和灰度 MUX、TB6612 PWM、编码器冲突），115200 8N1 |
| 2. 新增 UART 发送驱动 | `bsp/` + `hal/hal_uart.h` | 最简即可：阻塞发送一行字符串，波特率 115200 下发 1 行约 1ms，远超 5ms 节拍预算 |
| 3. 加速度来源 | `app/line_task.c` | **本工程无 IMU**。可由 `encoder_speed` 的轮速微分为纵向加速度：`a ≈ (v_k - v_{k-1}) / dt`，再做 EMA 平滑并限幅 |

第 3 条是关键设计决策：轮速微分在直线段够用，但打滑时噪声大，
建议 `dt` 用固定 5 ms 节拍、对结果做 EMA，并用 `clamp(±1500)` 兜底。

发送频率不必每拍都发，**20 ms 一次（50 Hz）** 足够——B 侧前馈每拍刷新，但输入本身变化慢。

## 5. 联调验收

1. A 侧串口助手能收到合法的 `A,xxx*HH`
2. B 侧 `ball_ctrl_frame_count()` 正常递增，`ball_ctrl_crc_err()` 不涨
3. B 侧 `ball_ctrl_accel()` 读数与 A 侧实际输出的加速度一致
4. 手动推车加减速，观察摆杆是否朝抵消方向动作（方向反了就改 `BALL_INERTIA_DIRECTION`）

## 6. 待决策：ASCII 是否要换成二进制帧

B 侧作者在根 README 里把 ASCII 标为「过渡帧」，计划后续改二进制。这个决定要一起拍板，
先摆出量化依据：

**带宽核算**：一行 `A,820*57\n` 约 10 字节，按 20 ms 周期（50 Hz）发送 → **500 B/s**。
115200 8N1 实际约 11.5 KB/s，**占用不到 4.5%**。带宽不是瓶颈。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| ASCII（现状） | 串口助手直接肉眼看到 `A,820`，无需查表；A 侧 `sprintf` 即可；调试期效率最高 | 解析要 `strtol`/`strchr`，代码略长；无严格类型 |
| 二进制 | 字段类型严格、省带宽 | 调试必须靠抓包工具；两边结构体/字节序必须严格一致，任何一侧改动都会静默出错 |

**建议**：比赛项目保持 ASCII。数据量只有每秒几百字节，二进制换来的收益几乎为零，
却要付出联调期排障成本。**除非**后续要扩到高频大载荷（例如 100 Hz 传完整球状态 + 车辆状态），
再考虑切换。

**若确实要切**：双方同一天切换，且 B 侧在一段时间内**同时保留 ASCII 解析**
（现有解析器已经是「按 tag 分发」，加分支成本很低），避免一方没更新导致整条链路哑掉。
